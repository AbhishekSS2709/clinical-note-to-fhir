# Clinical Note → FHIR

Extracts structured FHIR R4 clinical records (conditions, medications, allergies, vitals, procedures) from free-text clinical notes, via a QLoRA fine-tuned Qwen3-8B served side-by-side with its untouched base model.

## Why fine-tuning, not RAG

This task needs a **fixed output schema** and **cheap, high-volume inference** — retrieval solves neither. RAG earns its keep when an answer depends on fresh or per-query external knowledge; extracting the same five FHIR resource types from a self-contained note is a closed, schema-constrained transformation, not a knowledge-lookup problem. Fine-tuning bakes the schema into the model's weights, so every inference call is a single forward pass with grammar-constrained decoding — no retrieval index, no chunking, no context-window tax per request, and none of that infrastructure to keep in sync.

## How the data was built

Real clinical notes come with no ground truth. Rather than pay for labeling, or trust a bigger model's guesses as if they were gold, this pipeline runs the extraction task **backwards**:

```
Synthea  ──generates──▶  valid FHIR bundle  ──(this IS the gold label)
                               │
                               ▼
                      subset selection
                               │
                               ▼
                Qwen3-14B writes a clinical note
                      conditioned on that subset
                               │
                               ▼
                    (note, label) training pair
```

Synthea (MITRE, Apache 2.0) generates synthetic patients with valid FHIR R4 bundles — the label is correct by construction, with no teacher model and no circular evaluation. This is the *asymmetry principle* from **SynthIE** (Josifoski et al., [arXiv:2303.04132](https://arxiv.org/abs/2303.04132)): for tasks with structured outputs, generating plausible text *from* a target structure is far easier for an LLM than extracting the structure from text, so the easy direction is run to manufacture data for the hard one.

**Subset selection is the critical correctness detail.** A Synthea bundle is a patient's *entire* history; a real clinical note only ever mentions a slice of it. Labeling a generated note with the full bundle would train the model to emit facts absent from the text — i.e. train it to hallucinate. Instead, a realistic subset (current active conditions, current meds, this encounter's vitals, relevant history) is sampled first, *that subset becomes the label*, and the note is generated conditioned on exactly that subset — never on the full bundle. The note generator is prompted to mention every fact in the subset and invent nothing beyond demographics and filler.

## Honest limitations

- **This is a narrowed FHIR profile, not full FHIR conformance.** `profile.py` covers exactly five resource types (Condition, MedicationStatement, AllergyIntolerance, Observation-vitals, Procedure) with flat field sets chosen for what an extraction model can plausibly recover from text — not the full FHIR R4 resource surface.
- **The Synthea bundle parser has only been validated against a hand-authored fixture, never against genuine Synthea output.** `synthea.py`'s `parse_bundle` passes its tests against `tests/fixtures/bundle_sample.json`, which was written by hand to match Synthea's documented shape. It has not yet been run against a real `run_synthea` export — re-verification against genuine output is required before trusting the parsed corpus.
- **Training data is synthetic; the synthetic→real transfer gap is unmeasured.** Every training and eval example so far is a Synthea-bundle-conditioned, LLM-generated note. No held-out set of real (or even human-written synthetic) clinical notes has been scored yet, so how well this model generalizes off-distribution is currently unknown.

## Reproduce it

```bash
make install
make data
make train
make merge
make eval
make serve
```

`merge` must run before `eval`/`serve` for the tuned model: vLLM cannot load a bare PEFT adapter directory as `model=`, only merged weights (`scripts/merge_adapter.py` produces `outputs/merged/qlora-8b`).
